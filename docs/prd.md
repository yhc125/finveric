## 서비스 정의

서비스명은 **핀베릭(FINVERIC)**이다. 팀 조사는 가칭 "세일즈 블랙박스"를 쓴다. 이름은 팀이 정한다. 정하기 전까지 코드와 문서는 FINVERIC을 쓴다.

**투자상품 판매 과정을 단계마다 공동 원장에 기록하고, 판매사를 거치지 않고 검증하게 하는 판매 기록·검증 레이어다.**

FINVERIC은 새 판매 앱이 아니다. 판매사의 앱과 창구 시스템 아래에 연결한다. 원장에 기록하는 단계는 투자성향 진단(모든 회차), 적합성 판정, 설명 확인, 청약, 최종 의사 확인이다. 원장은 앞 단계 기록이 없으면 다음 단계를 거절한다. 등록하지 않은 기준으로는 판정을 기록할 수 없다. 원장에는 기록을 고치거나 지우는 기능이 없다.

FINVERIC을 쓰는 곳은 판매사다. 기존 판매 관리 시스템을 유지하면서 기록 검증 기능을 보완한다. 판매사는 진단 기준과 판매하는 상품을 등록하고 고객별 민감한 원문을 기존 보관 체계에서 관리한다. FINVERIC은 등록 기준에 따른 판정 증명, 원장 기록, 검증 화면을 제공한다. MVP의 증권사 앱과 진단 API는 연동 흐름의 예시다. 판매 원칙과 원본 보관의 책임은 판매사에 남는다. [범위 결정](adr/0009-verification-supplement.md)

대상 상품은 펀드와 ELS 같은 금융투자상품이다. 상품 유형은 상품 속성으로 둔다. 시연은 기록이 가장 많이 필요한 고난도 금융투자상품(ELS)을 중심으로 한다.

해결할 핵심 문제는 분쟁 당사자인 판매사가 판매 기록을 혼자 보관한다는 점이다. 그래서 세 조건을 함께 만족해야 한다.

1. **공동 보관.** 이해관계가 다른 기관이 같은 기록을 각자 보관한다.
2. **변경 불가.** 기록을 입력한 판매사도 나중에 고치거나 지울 수 없다.
3. **독립 검증.** 고객과 감독기관이 판매사를 거치지 않고 기록을 확인한다.

## 문제 유형

사례와 수치의 출처는 [시장 조사](market-research.md)에 둔다.

| 유형 | 사례 (팀 조사) | 제공할 기능 | 원장이 하는 일 |

| A. 사후 변경·임의 작성 | 가입 결정 뒤 투자성향 변경(KB증권 라임, 2020), 고객 확인 없이 확인서 작성(경남은행 라임, 2022), 서류 사후 보완(DLF, 2019) | 진단 회차와 판정을 기록 시점에 고정한다. | 같은 기록의 변경 요청을 거절한다. 수정 함수가 없다. |

| C. 판매 당시 절차 위반 | 반복 성향 분석(하나은행 양매도 ETN, 2019), 성향 분석 부실 설계와 설명 누락(H지수 ELS, 2024) | 재진단 반복, 부적합 가입, 짧은 설명 확인 시간을 위험 신호로 표시한다. | 근거 기록을 보관한다. 위반 자체를 막지는 못한다. |

발생 빈도, 처리 비용, 구매 의향은 아직 검증하지 않았다. 파일럿과 담당자 인터뷰로 확인한다.

## 제도 요건

원장과 화면은 아래 요건을 기준으로 설계한다. 근거와 원문 링크는 [시장 조사](market-research.md#제도와-판매-절차)에 둔다. 2026-11-12에 원문 기사·공식 자료로 대조했다. 고난도 상품의 녹취·숙려(2021-05-10 시행, 숙려 2영업일 이상, 고령 기준 65세)와 2025-02-26 개선방안(판매대상 고객군, 상품명 표시)을 확인했다. 투자성향 5단계·위험등급 6단계, 6개 필수 정보, 점수·추출 방식, 설명서 배치 요건은 아직 원문을 대조하지 않았다.

| 요건 | 내용 | 반영 |
| --- | --- | --- |
| 투자자 정보 | 거래 목적, 재산 상황, 투자 경험, 상품 이해도, 위험에 대한 태도, 연령 6개를 파악한다. | 진단 기준 편집기는 6개 범주를 모두 요구한다. |
| 투자성향 | 5단계다. 안정형, 안정추구형, 위험중립형, 적극투자형, 공격투자형. | 회로가 1~5단계를 계산한다. |
| 상품 위험등급 | 6단계다. 1등급이 매우 높은 위험, 6등급이 매우 낮은 위험이다. | 상품 버전에 고정한다. |
| 판단 방식 | 점수 방식과 추출 방식을 함께 쓴다. 추출 방식은 특정 답변과 맞지 않는 상품을 권유 대상에서 뺀다. | 회로가 점수 합계와 추출 조건을 함께 계산한다. |
| 판매대상 고객군 | 상품별로 미리 정한다. 해당하지 않는 고객에게는 권유하지 않는다. 예: 원금비보장 ELS는 원금 전액 손실을 감내할 수 있는 고객에게만 권유한다. | 추출 조건으로 표현한다. 상품 화면에 문구로 표시한다. |
| 부적합 | 권유하지 않는다. 고객이 스스로 원하면 부적합 사실을 알리고 확인을 받는다. | 추가 위험 확인을 청약 거래에 기록한다. |
| 고난도 금융투자상품 | 구조가 복잡하고 최대 원금손실 가능금액이 원금의 20%를 넘는다. 상품명 앞에 `고난도 금융투자상품`을 표시한다. | 상품 속성으로 등록한다. |
| 녹취·숙려 | 고난도 상품을 개인 일반투자자에게 팔면 전 과정을 녹취한다. 65세 이상 고객이나 부적합 고객에게 파생결합증권을 팔 때도 녹취와 숙려를 적용한다. 녹취를 거부하면 판매하지 않는다. | 원장이 녹취 파일 지문을 요구한다. 시연은 모의 파일을 쓴다. |
| 숙려기간 | 고난도 상품은 청약 뒤 2영업일 이상이다. 이 기간에 위험과 최대 손실 금액을 다시 알린다. | 원장이 최소 경과 시간 전의 최종 확인을 거절한다. |
| 최종 의사 확인 | 숙려기간 뒤 다시 확인해야 계약이 확정된다. 확인하지 않으면 청약을 집행하지 않는다. | 최종 확인 거래가 가입을 확정한다. |
| 설명서 | 최상단에 부적합 고객 유형과 손실 사례를 둔다. | 핵심 설명 카드의 첫 장에 둔다. |

| 공인전자문서센터 | 완성된 증명서를 보관한다. MVP에서 제외한다. | 없음 |

- 고객은 FINVERIC 화면을 직접 쓰지 않는다. 고객 검증은 증권사 앱 예시의 기록 확인 화면(`/channel/verify`)으로 보여 준다. 판매사와 독립된 고객 확인 경로의 운영 주체는 MVP 이후에 정한다. [결정 기록](adr/0007-openapi-and-channel-sample-app.md)
- 상품을 만든 제조사(운용사, 발행사)는 client가 아니다. 판매원칙 책임이 판매사에 있기 때문이다. 제조사는 투자설명서 내용의 정확성에 책임을 진다. 화면에는 상품 정보로 운용사·발행사 이름만 표시한다.
- 위험등급은 판매사가 정한다. ELS는 발행사 신용위험을 반영한다(팀 조사).
- 실제 판매·보관·감독 책임을 컨트랙트에 옮긴다고 가정하지 않는다.

## 원장, ZKP, 원본의 역할

- 원장에는 검증에 필요한 정보와 개인정보가 없는 공통 기준·상품 설명서 원문을 남긴다. 고객별 상세 답변과 총점, 임의값, 녹취 원문은 남기지 않는다. 가명 ID와 판정 결과가 공개되므로 익명화나 개인정보 위험 제거를 보장하지 않는다.
- 고객별 민감한 원문은 판매사의 기존 보관 체계가 관리하는 방향이다. MVP는 로컬 JSON 파일 또는 Upstash Redis로 오프체인 보관을 재현하며 실제 증권사 원문 저장소에는 연결하지 않았다. 권한 있는 요청은 증명서와 원본 묶음을 내려받을 수 있다.
- ZKP는 "이 답변으로, 원장에 등록된 진단 기준에 따라 이 투자성향을 계산했다"를 답변 공개 없이 증명한다. 해시만으로는 기준대로 계산했는지 증명하지 못한다. 그래서 감독기관도 원문 없이 판정을 확인할 수 있다.
- ZKP가 증명하지 않는 것이 있다. 최초 입력의 사실성, 고객의 실제 이해, 실제 서명자 신원이다.
- 해시와 증명은 원본 보관을 대체하지 않는다. 판매사와 고객이 모두 원본을 잃으면 내용을 복구할 수 없다.
- 실제 서비스는 허가형 블록체인을 가정한다. 판매사, 감독기관, 협회가 노드를 운영한다. MVP는 로컬 Anvil과 공개 테스트넷 Sepolia에서 시연한다. [결정 기록](adr/0003-sepolia-ledger.md)
- 블록체인의 추가 가치는 독립 검증, 공동 변경 통제, 분쟁 근거 확인 비용으로 평가한다. 참여 기관이 한 운영자를 충분히 믿으면 공통 DB와 전자서명으로도 처리할 수 있다. 한 기관이 모든 키와 변경 권한을 가지면 이점이 줄어든다.
- 토큰증권 제도가 2027-02-04에 시행된다. 증권사는 분산원장 노드를 준비한다. 같은 노드 인프라에 판매 기록 원장을 더하는 방안은 후속으로 검토한다. 비용 절감 효과는 가정이다.

| 청약·확인 | 판매 ID, 상품 버전, 금액, 사용 회차, 적합성·확인 상태, 녹취 지문, 시각 등은 원장에 남는다. 관리자 승인 서명도 청약 거래 입력으로 공개된다. 개인 서명 키와는 다르다. | `FundLedger.sol`, `modules/enrollment.ts` |
| 재진단 사유·승인 검토 기록 | 선택형 코드와 승인 시각을 오프체인에 보관한다. 일반 API 응답, trace, 원본 다운로드, 원장에는 추가하지 않는다. | `repositories/sales.ts`, `modules/review.ts` |

회로의 공개 신호는 위 9개다. 답변과 salt는 비공개 입력이고 총점은 내부 계산값이다. 기준의 점수표·추출 조건 등은 회로 입력이지만 이미 공통 원문으로 공개되므로 비밀 정보가 아니다. 회로는 등록 기준 해시, 답변 범위, 커밋먼트와 판정 결과의 정합성을 검증한다. 상품 적합성, 관리자 서명, 녹취 지문 존재, 숙려 경과 검사는 원장이 별도로 수행한다. 투자성향으로 총점 구간을 추정할 수 있고 고령 여부도 드러난다.

ZKP는 입력의 진실성, 고객 이해, 담당자의 실제 검토, 설명·녹취의 충실성, 법규 준수 전체를 증명하지 않는다. 검증 결과의 `일치`도 제출 자료와 기록의 일치를 뜻한다. 원문을 공개하지 않고 판정을 검증하는 것과 API 운영자에게도 원문을 숨기는 것은 다르다.

API의 요청 로거는 꺼져 있고 일반 조회와 trace는 공개 필드만 만든다. 원본 다운로드에는 접근 코드·API 키·고객 세션별 권한 경계가 적용된다. 단, 접근 통제를 설정하지 않은 로컬 모드와 공개 콘솔 시연은 실고객 데이터 운영 환경이 아니다. 프록시·호스팅 로그, 브라우저 저장소, 저장소 암호화·보존 정책까지 보호됨을 입증한 것은 아니다. 실제 개인정보를 시연에 넣지 않는다.

## 핵심 기능

1. **기준 버전 등록.** 판매사는 진단 기준을 버전으로 등록한다. 진단 기준은 문항, 선택지 점수, 추출 조건, 등급 구간, 적합성 기준이다. 판매하는 상품의 설명서 버전, 위험등급, 판매대상 고객군도 등록한다. 등록한 버전은 고칠 수 없다. 바꾸려면 새 버전을 등록한다.
2. **회차별 진단 기록.** 진단할 때마다 원장에 기록한다. 회차는 판매 건이 아니라 고객 가명 ID로 센다. 고객이 가입을 중단하고 다시 시작해도 회차가 이어진다.
3. **ZKP 판정.** 회로가 선택지 범위, 점수 합계, 추출 조건을 검사한다. 회로는 투자성향과 권유 가능 최고 위험등급을 계산한다. 원장은 증명과 기준 해시를 검사한다.
4. **단계 통제.** 원장은 진단 → 청약 → 숙려기간 → 최종 확인 순서를 강제한다. 조건은 [판매 절차와 원장 기록](#판매-절차와-원장-기록)을 따른다.
5. **가입 증명서와 독립 검증.** 가입이 확정되면 증명서를 발급한다. 증명서에는 증명서 번호(판매 ID)와 확인 링크가 있다. QR 표시는 후속이다. 증권사 앱 예시의 기록 확인 화면과 감독기관 화면은 판매사 API 없이 원장과 대조한다. 결과는 `일치`, `불일치`, `기록 없음` 세 가지로 표시한다.
6. **위험 신호.** 판매사와 감독기관 화면에 위험 신호를 표시한다. 근거는 원장 이벤트다. 신호와 기준값은 [위험 신호](#위험-신호)를 따른다.
7. **원본 보관 연동.** 공인전자문서센터 보관은 후속이다. MVP는 고객 다운로드로 한정한다.

## 판매 절차와 원장 기록

원장 설계는 [결정 기록 0005](adr/0005-ledger-v5-registered-rules.md)를 따른다. 이벤트 이름은 구현에서 정한다.

| 단계 | 판매 채널 화면 | 원장 기록 | 송신자 | 원장이 거절하는 경우 |
| --- | --- | --- | --- | --- |
| 0. 기준 등록 | (client) 진단 기준 관리, 상품 관리 | 진단 기준 해시, 상품 버전(상품 유형, 설명서 지문, 위험등급, 고난도 여부, 파생결합증권 여부) | 판매사 키 | 같은 버전을 다시 등록 |
| 1. 진단 (회차마다) | 한 화면에 한 문항, 결과 | 고객 가명 ID, 회차, 기준 해시, 커밋먼트, 투자성향, 권유 가능 최고 위험등급, 고령 표시, 증명 | 판매사 키 | 등록하지 않은 기준, 잘못된 증명, 회차 건너뛰기·중복 |
| 2. 적합성·설명·청약 | 적합성 확인, 핵심 설명 카드 5장, 청약 | 판매 ID, 상품 버전, 사용한 회차, 적합 여부, 설명 확인과 확인 시간, 필요한 추가 위험 확인·관리자 승인·녹취 지문 | 고객 키 | 최신 회차가 아님, 설명 확인 없음, 부적합인데 추가 위험 확인 없음, 3회차 이상인데 관리자 승인 없음, 녹취 대상인데 녹취 지문 없음 |
| 3. 숙려기간 | 숙려 안내, 위험과 최대 손실 재고지 | 없음 | — | — |
| 4. 최종 확인 | 최종 의사 확인, 증명서 | 가입 확정 | 고객 키 | 숙려기간 전, 이미 확정·철회한 판매 건 |
| 4-1. 철회 | 확인하지 않거나 철회 | 철회 | 고객 키 | 이미 확정한 판매 건 |
| 5. 모의 결제 | 청약 결과(모의) | 모의 결제 상태 | 인프라 키 | 확정 전 |

- **고객 가명 ID.** 판매사 비밀값과 고객 번호로 만든 해시다. 외부에서는 실제 고객을 알 수 없다. 분쟁 때는 판매사가 연결 정보를 낸다. 판매사 사이의 연결은 하지 않는다(후속 검토).
- **누적 회차 번호.** 원장이 고객 가명 ID별로 정한다. 날짜·판매 건·가입 중단과 무관하게 이어지며 건너뛰거나 다시 쓸 수 없다.
- **일별 횟수.** 한국 시간(UTC+9) 00:00부터 다음 날 00:00 전까지 기록된 진단을 센다. 일별 재진단은 그중 누적 회차가 2 이상인 기록 수다. 전날 처음 진단한 고객은 오늘 첫 진단도 재진단이다. 일별 횟수는 표시용이며 원장 회차나 승인 조건을 초기화하지 않는다.
- **관리자 승인.** 누적 3회차 이상 고객의 청약에 승인을 요구하는 것은 FINVERIC 자체 내부통제 정책이다. 법령이나 감독기관이 정한 횟수 기준이라고 주장하지 않는다. 승인은 청약 전에 별도 키로 서명하고 판매 ID·최신 누적 회차에 묶는다. 새 회차를 기록하면 다시 승인해야 한다.
- **재진단 사유.** API의 `reassessmentReason`으로 응답 정정·상황 변경·재확인 중 하나를 선택한다. 최초 진단에는 보관하지 않는다. 기존 연동과 시연을 위해 선택 사항이며 미입력은 사유가 확인되었다는 뜻이 아니다.
- **승인 검토 기록.** `reason`은 정정·상황 변경·재확인 검토 중 하나, `reviewBasis`는 회차 이력·위험 신호·고객 확인 자료 중 복수 선택이다. 서버 시각과 회차별 승인 이력을 보관한다. 같은 회차의 중복 승인은 덮어쓰지 않는다. 자유문·첨부파일을 받지 않아 개인정보의 우발적 입력을 줄인다. 실제 검토 자료, 담당자 신원, 사유의 진실성이나 변경 방지를 증명하지 않으며 전용 조회·감사 화면은 후속이다.
- **최신 회차.** 청약은 그 고객의 가장 최근 회차를 써야 한다. 더 유리한 이전 결과를 골라 쓰지 못한다.
- **적합 여부.** 상품 위험등급이 권유 가능 최고 위험등급보다 위험하면 부적합이다. 원장이 계산한다.
- **녹취 대상.** 상품이 고난도이거나, 파생결합증권을 65세 이상 고객이나 부적합 고객에게 팔 때다. 원장이 계산한다.
- **숙려기간 대상.** 녹취 대상과 같다. 영업일 계산은 판매사 시스템이 한다. 원장은 배포 때 정한 최소 경과 시간만 검사한다. 시연 값은 Anvil과 Sepolia 모두 60초다. 시연용 가정이다.
- **설명 확인 시간.** 판매사 앱이 보고한 값이다. 원장은 값을 검증하지 않고 기록만 한다.
- 고객이 중단해도 진단 기록은 남는다. 청약하지 않은 진단은 위험 신호 집계에 들어간다.

## MVP 범위

- 가상 상품 3종을 쓴다. 주 시연 상품은 1등급 원금비보장 ELS다. 펀드와 ELB는 상품 유형과 등급별 소속을 보여 준다.
- 판매 증권사 한 곳, 소비자보호 담당, 가상 고객 한 명, 감독기관을 시연한다. 판매사별 지표가 필요하면 시연용 판매사로 은행 한 곳을 더한다(미정).
- 판매사 기록, 관리자 승인, 모의 결제 연동에 별도 테스트 키를 쓴다. 고객 확인도 모의 키로 시연한다.
- 원장 v5에서 진단 기준 v1과 상품별 설명서 v1을 쓴다.
- 실제 ZKP 생성·검증과 원장 거래를 시연한다. 개발과 반복 검사는 Anvil에서 한다. 외부 시연 원장은 Sepolia다. 배포 구성과 상태는 [배포 문서](deploy.md)를 따른다. 본인인증, 전자서명, 녹취, 자금 이체, 발행은 모의로 처리한다. 화면은 실제 서비스처럼 만들고 `시연`, `모의` 표시를 붙이지 않는다.
- 만기, 조기상환, 수익 지급, 토큰 발행은 이번 범위에서 제외한다. 실제 증권사 원문 저장소 연동, 허가형 블록체인 구축, 기관별 독립 키 관리는 상용화 과제다. 업무 효율 비교 실험은 별도 작업으로 진행한다.
- 고객 다운로드와 독립 검증을 포함한다. 공인전자문서센터·상용 보관소 연동은 제외한다.
- 웹은 Vite 앱 하나에 페이지 네 개다. 진입 화면(`/`), 판매사 콘솔(`/client/`), 증권사 앱 예시(`/channel/`), 감독기관 화면(`/auditor/`)이다. [결정 기록](adr/0006-seller-console-and-single-web-app.md), [0007](adr/0007-openapi-and-channel-sample-app.md)
- API는 OpenAPI 3.1 문서(`/api/openapi.json`)와 문서 화면(`/api/docs`)을 제공한다. 판매사 앱은 이 문서의 `판매 채널 연동` API로 고객 흐름을 만든다. 증권사 앱 서버는 판매사 콘솔에서 발급한 API 키로 부른다. 키는 `판매 채널 연동` API만 부를 수 있다. [결정 기록](adr/0008-api-keys.md)
- 외부 시연은 Vercel의 웹·API 함수와 Upstash Redis로 배포한다. 상시 서버는 두지 않는다. 로컬 시연은 Docker 한 명령으로 실행한다. [배포 문서](deploy.md)

### 시연 진단 기준 v1

값은 모두 시연용 가정이다. 실제 기준은 판매사의 투자권유준칙을 따른다.

| 범주 | 문항 | 0점 | 1점 | 2점 |
| --- | --- | --- | --- | --- |
| 연령 | 나이 | 65세 이상 (고령 표시) | 50~64세 | 49세 이하 |
| 거래 목적 | 투자 목적 | 원금 보존 (추출: 5등급까지) | 예금 이자 이상의 수익 | 높은 수익 |
| 재산 상황 | 금융자산 중 이번 투자 비중 | 30% 초과 | 10~30% | 10% 이하 |
| 투자 경험 | 투자해 본 상품 | 예금·채권 | 펀드 | ELS·파생상품 |
| 상품 이해도 | ELS 구조 이해 | 모름 | 들어 본 적 있음 | 녹인과 조기상환을 설명할 수 있음 |
| 위험 태도 | 감내할 수 있는 손실 | 원금 손실 불가 (추출: 5등급까지) | 원금 20%까지 (추출: 2등급까지) | 원금 전액 |

| 합계 | 투자성향 | 권유 가능 위험등급 |
| --- | --- | --- |
| 0~2점 | 안정형 | 6등급 |
| 3~4점 | 안정추구형 | 5~6등급 |
| 5~6점 | 위험중립형 | 3~6등급 |
| 7~9점 | 적극투자형 | 2~6등급 |
| 10~12점 | 공격투자형 | 1~6등급 |

- 추출 조건은 등급표보다 우선한다. 예를 들어 공격투자형이어도 "원금 20%까지"를 고르면 2~6등급만 권유한다.
- 원금비보장 1등급 ELS의 판매대상 고객군 "원금 전액 손실 감내 가능"은 위험 태도 2점과 공격투자형으로 표현한다.

| 가상 원금지급형 ELB | 증권사(발행) | 5등급 | 원금지급 | 안정추구형 이상 |

제조사는 상품 정보로만 표시한다. 상품 등록과 위험등급 결정은 판매 증권사가 한다.

시연 청약 금액은 1,000만 원이다. 결제와 발행은 모의 처리다.

## 위험 신호

신호 기준값은 시연용 가정이다. 판매사가 바꿀 수 있게 하는 기능은 후속이다.

| 신호 | 조건 | 근거 기록 |

| 재진단 반복 | 같은 고객 가명 ID의 누적 진단이 3회 이상(일별 아님) | 진단 기록 |
| 결과 상승 뒤 청약 | 직전 회차보다 투자성향이 오른 회차로 청약 | 진단 기록, 청약 기록 |

| auditor · 분쟁 조회 | 감독기관 | 판매 ID나 고객 가명 ID로 단계별 원장 대조, 판매사 제출 원본 대조 |
| auditor · 기준 감사 | 감독기관 | 진단 기준 버전 목록, 원문 해시 대조, 버전 간 차이 |
| auditor · 상품 감사 | 감독기관 | 상품·설명서 버전과 위험등급 이력, 설명서 원문 대조 |
| auditor · 위험 신호 | 감독기관 | client와 같은 신호를 원장 이벤트만으로 계산 |
| auditor · 보고서 | 감독기관 | 선택한 범위의 대조 결과 내보내기 |

화면 원칙(팀 조사 6.1):

- 감독기관 화면에도 개인정보 원문을 표시하지 않는다. 원문은 판매사가 분쟁 절차에 따라 내고, 화면은 원장과 일치하는지만 판단한다.
- 고객 화면은 블록체인 용어를 숨긴다. 예: "원장 기록 완료" 대신 "기록이 안전하게 보관됐어요".
- 검증 결과는 `일치`, `불일치`, `기록 없음` 세 상태만 쓴다. 블록 번호와 해시는 상세 영역에 접어 둔다.
- 기본색은 파랑, 경고와 불일치는 주황이다. 색과 함께 아이콘과 글자로도 구분한다.
- 상품명 앞에 `고난도 금융투자상품`을 표시한다. 설명 화면 최상단에 부적합 고객 유형과 손실 사례를 둔다.

## 기말 시연 시나리오

목표 시연 시간은 약 6~8분이다. 테스트넷 대기 시간은 별도다. Sepolia에서는 거래마다 약 12초를 기다린다. 시간은 실제 리허설로 확인한다.

| 순서 | 발표자의 동작 | 확인할 결과 |
| --- | --- | --- |
| 1. 기준 등록 | 판매 증권사가 진단 기준 v1과 판매할 상품 3종을 원장에 등록한다. | 감독기관의 기준 감사에서 같은 기준 해시를 확인한다. |
| 2. 진단과 중단 | 고객이 1등급 ELS를 고르고 진단한다. 위험중립형이 나온다. 가입을 중단한다. | 진단 1회차가 원장에 남는다. |
| 3. 다시 시작 | 같은 고객이 다시 가입을 시작해 두 번 더 진단한다. 적극투자형, 공격투자형 순서다. 3회차의 위험 태도는 "원금 20%까지"다. | 회차가 2, 3으로 이어진다. 3회차 경고와 관리자 승인 요청을 표시한다. |
| 4. 관리자 승인 | 소비자보호 담당이 회차 이력과 위험 신호를 보고 승인한다. | 재진단 반복 신호와 회차마다 오른 투자성향을 확인한다. |
| 5. 부적합 청약 | 1등급 ELS는 추출 조건 때문에 부적합이다. 고객이 직접 원해 추가 위험을 확인한다. 녹취(모의)와 핵심 설명 카드 5장을 확인하고 청약한다. | 청약 거래가 성공한다. 숙려기간이 시작된다. |
| 6. 숙려와 확정 | 숙려기간 동안 남은 시간을 보여 준다. 최종 확인 버튼은 남은 시간이 끝날 때까지 막혀 있다. 기간이 지나면 최종 확인한다. | 숙려 중에는 확정할 수 없다. 기간이 지나면 가입이 확정되고 증명서가 나온다. |
| 7. 사후 변경 시도 | 판매사가 API(`POST /api/demo/tamper`)로 2회차 결과를 다시 기록하려 한다. 내 가입 기록에서 내려받은 원본의 답변 하나를 직접 바꾼다. | 원장이 `InvalidAttempt`로 거절한다. |
| 8. 고객 검증 | 증권사 앱 예시의 기록 확인 탭에서 증명서 번호로 검증한다. 바꾼 원본 파일로도 검증한다. | 원래 기록은 `일치`, 바꾼 원본은 `불일치`(원본 답변 대조)다. |
| 9. 감독기관 조회 | 분쟁 조회에서 같은 판매 ID를 연다. | 단계별 대조, 기준 이력, 위험 신호를 판매사 API 없이 확인한다. |

사후 변경 시나리오는 탐지와 덮어쓰기 거절을 보여 준다. 판매사의 원본 삭제를 원장만으로 복구한다고 설명하지 않는다.

## 완료 기준

| 상황 | 기대 결과 |
| --- | --- |
| 진단 기준 등록 | 같은 버전을 다시 등록하면 거절한다. 원문을 바꾸면 해시가 달라진다. |
| 등록하지 않은 기준이나 바꾼 기준 값으로 증명 | 유효한 증명을 만들 수 없거나 원장이 거절한다. |
| 규칙 밖 선택지 | 유효한 증명을 만들 수 없다. |
| 회차 기록 | 원장이 회차를 1부터 차례로 매긴다. 건너뛰기·중복·재기록을 거절한다. |
| 중단 후 다시 시작 | 같은 고객 가명 ID의 회차가 이어진다. |
| 추출 조건 | 추출 답변을 고르면 투자성향과 관계없이 권유 가능 위험등급이 제한된다. |
| 이전 회차로 청약 | 최신 회차가 아니면 거절한다. |
| 3회차 이상 청약 | 관리자 승인이 없으면 거절한다. |
| 부적합 청약 | 추가 위험 확인이 없으면 거절한다. |
| 녹취 대상 청약 | 녹취 지문이 없으면 거절한다. |
| 설명 확인 누락 | 청약을 거절한다. |
| 숙려기간 전 최종 확인 | 거절한다. |
| 확정·철회한 판매 건의 재확인 | 거절한다. |
| 증명 재사용 | 다른 고객 가명 ID, 회차, 원장, 체인의 증명은 거절한다. |
| 권한 없는 송신자 | 거절한다. |
| 거래 영수증 대기·실패 | 완료로 표시하지 않는다. 실패 이유와 현재 상태를 구분한다. |
| 고객 원본과 바꾼 사본 | 원본은 `일치`, 바꾼 사본은 `불일치`다. |
| 원장에 없는 판매 ID | `기록 없음`이다. |
| 가입 기록 확인과 감독기관 조회 | 판매사 API 없이 지정 RPC·컨트랙트로 확인한다. |
| 위험 신호 | client와 auditor가 같은 이벤트에서 같은 신호를 계산한다. |
| 공개 데이터·로그 검사 | 답변, 총점, 임의값, 고객 번호, 서명 키를 공개하지 않는다. |

Sepolia에는 가상 상품 식별자, 고객 가명 ID, 판매 ID, 커밋먼트, 회차, 투자성향, 권유 가능 위험등급, 고령 표시, 확인 기록, 증명, 거래 이력이 공개된다. 가입을 중단한 고객의 진단 결과도 남는다. 공개된 투자성향으로 총점 구간을 알 수 있다. 실제 서비스의 공개 범위와 네트워크는 별도로 정한다.

## 정하지 않은 것

- **서비스 이름.** FINVERIC과 가칭 "세일즈 블랙박스" 중에서 팀이 정한다. 그림과 화면 캡처를 다시 만들기 전에 정한다.
- **시연 판매사 수.** 감독기관의 판매사별 지표를 보이려면 두 곳이 필요하다.
- **기준값.** 진단 기준 v1, 위험 신호 기준값, 숙려 시연 시간은 시연용 가정이다.
- **제도 요건 원문.** 2026-11-12에 팀 조사를 시장 조사에 옮기고 원문과 대조했다. 금소법 과태료 상한(적합성·적정성 위반 3천만 원 이하)과 H지수 ELS 손실 수치(17만 계좌, 원금 10조 4,000억 원 중 손실 4조 6,000억 원)는 확인했다. 금감원의 "재분석 시 관리자 승인" 권고는 원문을 찾지 못했다. 이 권고를 누적 3회차 승인 조건의 근거로 쓰지 않는다. 횟수 조건은 FINVERIC 자체 정책으로 정했다. 나머지 미대조 항목은 시장 조사에 표시했다.

## 구현 순서와 현재 상태

1. **진입 화면과 메뉴 재구성.** 2026-11-12에 마쳤다.
2. **원장·회로 v5.** 진단 기준 데이터 모델, 범용 회로, 회차별 기록, 단계 통제, 검사. 2026-11-13에 마쳤다.
3. **client 관리 화면과 API.** 진단 기준 관리, 상품 관리, 판매·검토, 위험 신호. 2026-11-13에 마쳤다.
4. **판매 채널 전환.** 원장에 등록된 진단 기준으로 진단하고 청약·숙려·최종 확인까지 진행한다. 2026-11-13에 마쳤다.
5. **auditor 화면.** 대시보드, 분쟁 조회, 기준·상품 감사, 위험 신호, 보고서. 2026-11-13에 마쳤다.
6. **문서.** DESIGN.md, AGENTS.md, README, runbook, 화면 캡처. 2026-11-13에 마쳤다.

원장 v5와 핵심 시연 흐름은 유지한다. 2026-11-13의 검사 결과는 당시 기록이며 최신 검증은 PR의 실행 결과를 따른다. 남은 한계는 아래와 같다.

- Sepolia·Vercel 배포 구성과 운영 절차는 배포 문서를 따른다. [배포 문서](deploy.md)

- 관리자 승인은 판매 건마다 받는다. 같은 3회차 결과로 다른 상품에 청약하면 다시 승인한다.
