# 0006. client는 판매사 콘솔로 바꾸고, 웹은 Vite 앱 하나로 합친다

2026-11-12 · 결정됨(2026-11-13 구현) · [0001](0001-web-apps-by-audience.md)의 사용자 범위, 루트 경로, 앱 구성을 바꾼다 · client의 판매 채널 메뉴와 고객 검증 화면 위치는 [0007](0007-openapi-and-channel-sample-app.md)이 바꾼다 · 판매 시스템 대체 전제는 [0009](0009-verification-supplement.md)로 대체됨

## 맥락

[0001](0001-web-apps-by-audience.md)은 웹을 Vite 앱 두 개로 나눴다. client는 운용사·증권사·준법 담당자, auditor는 감독기관·외부 검증자가 쓴다. 투자자는 FINVERIC 화면을 직접 쓰지 않는다. 루트 `/`는 `/client/`로 보낸다. 개발 서버가 두 개(5173, 5174)라서 client는 auditor 주소를 환경 변수로 받는다.

금소법의 6대 판매원칙(적합성 원칙, 설명의무 등)은 금융상품판매업자가 지킨다. 불완전판매로 제재받는 쪽도 판매사다. H지수 ELS 제재(2026-11-04) 대상은 은행 7곳과 증권사 6곳이었다. 모두 판매사 자격이었다. 상품을 만든 제조사(운용사, 발행사)는 투자설명서 내용의 정확성에 책임을 진다. 판매 절차에 대한 책임은 지지 않는다.

FINVERIC이 남기는 기록은 판매사가 판매원칙을 지켰다는 증거다. 판매사는 판매 절차 시스템을 직접 만들고 운영하는 대신 FINVERIC을 쓰고, 상품과 판매에 집중한다.

사용자는 세 가지를 요청했다.

- client에서 진단 기준(질문지, 형식, 등급)과 등급별 상품을 관리한다.
- auditor에서 원장으로 검증하고 결과를 확인한다.
- 진입 화면을 만든다.

팀 조사(2026-11-12)는 "고객이 판매사를 거치지 않고 기록을 확인한다"를 핵심 주장으로 든다. 조사는 협회가 운영하는 고객 검증 페이지를 제안한다.

## 결정

- **client는 판매사 콘솔이다.** 판매사는 금융상품판매업자다. 증권사, 은행, 펀드를 직접 파는 자산운용사가 해당한다. 판매사는 진단 기준과 판매하는 상품을 등록한다. 진단 계산, 적합성 판정, 원장 기록, 증명, 검증 화면은 FINVERIC이 맡는다.
- **client 사용자는 판매사의 소비자보호 담당이다.** 진단 기준, 상품, 설명서 버전, 위험등급, 판매대상 고객군을 등록한다. 3회차 이상 진단한 고객의 청약에 관리자 승인을 한다. 위험 신호를 처리한다. 관리자 승인은 별도 키로 한다.
- **제조사는 client가 아니다.** 상품 정보에 운용사·발행사 이름만 표시한다. 제조사가 상품을 직접 등록하는 참여 방식은 MVP 이후 후보로 둔다.
- **client 메뉴:** 판매사 업무(대시보드, 진단 기준, 상품 관리, 판매·검토, 위험 신호, 온체인 처리)와 판매 채널(펀드 찾기, 가입하기, 내 가입 기록, 가입 기록 확인).
- **auditor는 감독기관 화면이다.** 메뉴는 대시보드, 분쟁 조회(판매 건과 파일을 원장과 대조), 기준 감사, 상품 감사, 위험 신호, 보고서다. 모든 자료는 지정 RPC의 원장에서 읽는다.
- **고객은 FINVERIC 화면을 직접 쓰지 않는다.** 고객 검증은 판매 채널 안의 가입 기록 확인 화면(`/client/channel/verify`)으로 보여 준다. 이 화면은 증권사 앱에서 고객이 증명서 번호나 파일로 기록을 확인하는 화면을 재현한다. 이 화면은 판매사 API를 쓰지 않고 브라우저가 지정 RPC로 원장과 대조한다. 결과는 `일치`, `불일치`, `기록 없음`이다. 실제 서비스에서 판매사와 독립된 고객 확인 경로를 누가 운영할지는 MVP 이후에 정한다.
- **루트 `/`는 진입 화면이다.** 역할 카드 2개(판매사 콘솔, 감독기관)와 연결된 원장·상태를 보여 준다. 상태는 `/api/health`로 읽는다. client와 auditor는 서로 링크하지 않는다. 두 페이지의 브랜드와 "처음 화면" 항목이 진입 화면으로 간다.
- **웹은 Vite 앱 하나(`apps/web`)에 페이지 세 개다.** `/`(진입 화면), `/client/`(판매사 콘솔), `/auditor/`(감독기관)다. 코드는 `src/entry`, `src/client`, `src/auditor`로 나눈다. 페이지마다 번들을 따로 만든다. 개발 서버는 하나(5173)다. 경로는 0001과 같다.
- **용어.** client 사용자는 "소비자보호 담당"이다. 3회차 이상 진단한 고객의 청약 승인은 "관리자 승인"이다. 팀 조사의 용어를 따른다. 팀 조사는 이 용어의 근거로 금감원 권고를 들었지만, 원문은 아직 찾지 못했다. "준법"은 쓰지 않는다. 코드 식별자는 v5 구현 때 맞춘다.
- **서비스 이름은 팀이 정할 때까지 FINVERIC을 쓴다.** 팀 조사의 가칭은 "세일즈 블랙박스"다.

## 이유

- 판매원칙을 지킬 책임이 있는 쪽이 판매사다. 이 서비스가 필요하고 비용을 낼 이유가 있는 쪽도 판매사다.
- 판매사가 위험등급을 정하므로 상품 등록도 판매사가 한다. 위험등급을 정하는 쪽과 등록하는 쪽이 같다.
- client 역할이 하나라서 메뉴와 권한 키가 단순하다.
- 고객 검증을 판매 채널 화면으로 두면 B2B·B2G 원칙에 예외가 생기지 않는다. 시연에서는 "판매사 API 없이 원장과 대조한다"를 보여 주면 충분하다.
- 웹을 한 앱으로 합치면 배포와 같은 한 주소와 경로로 개발한다. 개발 서버, 포트, 앱 사이 주소 변수가 줄어든다. 진입 화면이 특정 앱에 속하지 않는다.
- 페이지마다 번들을 나누므로 0001의 분리 이유가 유지된다. 판매사 업무 코드가 감독기관 화면에 실리지 않는다.

## 대가

- v4의 운용사 화면(상품·문서 관리)이 사라진다. 운용사가 여러 판매사에 같은 상품 버전을 한 번에 전달하는 기능도 MVP에서 빠진다.
- 판매사가 상품 정보를 직접 입력한다. 제조사의 설명서와 판매사가 등록한 설명서가 같은지는 원장이 보장하지 않는다.
- 고객 검증 화면은 판매사 콘솔(client)의 판매 채널 안에 있다. 판매사가 만든 화면이므로 실제 서비스의 독립 확인 경로가 아니다. 발표에서 이 점을 구분해 설명한다.
- client와 auditor가 같은 `package.json`, Vite 설정, 의존성을 쓴다. 한 페이지의 빌드 오류가 전체 빌드를 막는다.
- FINVERIC이 판매 절차 시스템을 제공해도 법적 책임은 옮겨 오지 않는다. 영업 자료에서 책임 이전처럼 설명하지 않는다.
- 화면 캡처와 그림을 다시 만든다.

## 검토한 대안

- **제조사도 client 역할로.** 운용사와 발행사가 상품을 한 번 등록하면 여러 판매사가 같은 버전을 쓴다. 제조사는 판매 절차에 대한 책임이 없어 이 서비스를 쓸 이유가 약하다. 역할과 키가 늘어난다.
- **auditor에 고객 검증 페이지(협회 운영 표시).** 판매사 밖의 확인 경로를 그대로 보여 준다. 고객이 쓰는 FINVERIC 화면이 생겨 B2B·B2G 원칙에 예외가 생긴다.
- **Vite 앱 두 개 유지.** 0001 그대로다. 진입 화면을 client 빌드의 두 번째 엔트리로 둬야 한다. 개발 서버 두 개와 앱 사이 주소 변수가 남는다.
- **진입 화면을 빌드 도구 없는 정적 HTML로.** 빌드가 필요 없다. 색과 스타일을 한 번 더 써야 하고 공통 컴포넌트를 쓰지 못한다.
- **진입 화면을 별도 React 앱으로.** 개발 서버, 포트, Docker 포트 설정이 하나씩 늘어난다.
- **진입 화면을 client 앱의 첫 화면으로.** 판매사 콘솔과 역할 선택이 섞인다. 감독기관이 판매사 콘솔을 거쳐 들어오게 된다.
